# fat32_reader 最小上板验证方案

**目标**：只初始化 TF 卡、遍历根目录、打开 `01.BMP`，确认
`file_size == 921654`（= 0x000E11B6）。

这一步过了，后面联调时再出问题就一定是别的环节（BMP 显示 / WAV / SDRAM / HDMI）。

---

## 0. 为什么单独做一个工程

在完整工程里 `fat32_reader` 出错的表现是"画面没出来"，
可能的原因有十几个：SPI 没初始化、图片不是 24 位、SDRAM 时序、HDMI 时序、
帧缓冲握手、HUD 覆盖…… 排查一次要综合+下载好几分钟。

摘出来之后，这个工程里**除了 FAT32 解析没有别的东西**，
数码管和 ILA 看到的每一个现象都只有一个解释。

---

## 1. 这个工程包含什么

```
probe/
  fat32_probe_top.v    测试顶层（POR + SD控制 + fat32 + 数码管）
  fat32_probe.adc      引脚约束（只含时钟/复位/TF卡/数码管）
  fat32_probe.al       TD 工程文件
  PROBE_TESTPLAN.md    本文
```

依赖的源文件（都在上一级目录，`.al` 里已经引好）：

| 文件 | 作用 |
|---|---|
| `../src/fat32_reader.v` | **被测对象** |
| `../src/sd_card/sd_card_top.v` | SD SPI 控制器（已验证过的） |
| `../src/sd_card/sd_card_sec_read_write.v` | 扇区收发 |
| `../src/sd_card/sd_card_cmd.v` | 命令层 |
| `../src/sd_card/spi_master.v` | SPI 物理层 |
| `../src/seg_scan.v` | 数码管扫描（原样复用） |

**不依赖**：PLL、SDRAM、HDMI 核、HUD、音频。全是普通 RTL。

**为什么不用 PLL**：`sd_card_top` 在 50MHz 下 `SPI_HIGH_SPEED_DIV=0`
正好给出 12.5MHz 读卡时钟（初始化 100kHz），符合 spec，
所以直接跑板时钟，省掉 PLL 依赖。完整工程跑 100MHz 时读卡是 25MHz，
两种对 FAT32 解析功能等价。

## 3. TF 卡要准备什么

**这一步只验证 `01.BMP` 一个文件**，所以卡上只要有它就行：

1. 卡用 Windows 格式化成 **FAT32**（分配单元大小默认）
2. 根目录放一个 `01.BMP`：
   - 640×480、24 位、未压缩
   - 文件大小必须正好 **921654 字节**
   - 如果手头没有，用 `tools/layout_sd.py` 里校验过的那张图，
     或者任意 640×480 24位 BMP（用画图另存为 24 位 BMP 即可）

> 这一步**不需要** `01.WAV`，也不需要 02~06。**只有一个文件更容易判断**：
> 如果 `found=0`，那一定是名字或格式的问题，不会是"匹配到别的文件了"。

`file_size` 报出来不是 921654 也很有信息量：
说明匹配到了别的文件（比如卷标、目录，或者 LFN 别名）。

## 4. 上板后看什么

### 4.1 数码管（位选/段选都是低有效）

**固定显示，不轮换。** 从左到右：

| 位 | 内容 |
|---|---|
| **物理最左 = d0** | 找到时 = file_size 十进制**最低位**；没找到时 = **state_code** |
| d1..d6 | 找到时 = 十进制的中间 6 位；没找到时**全灭** |
| **物理最右 = d7** | `9` = 上电启动标记（前 6 秒）；`F` = 找到了文件；`E` = 没找到 / 打开失败 |

> ⚠ **方向修正（2026-10-03 实测）**：本文件原先写"从左到右：d7 | d6..d0"，**那是反的**。
> `fat32_probe_top.v:460-473` 是 `seg_data_0 = s0`、`seg_data_7 = s7`，而
> `seg_data_0` 是**物理最左位**，`s7` 放的是标记。上板读数 `0······E` 正好印证：
> 右端 `E` 是标记、左端 `0` 是 state_code。

**01.BMP 正常应该显示 `4561290F`**（= 921654 的十进制**倒着写**，后面跟 `F`）：

```text
4 5 6 1 2 9 0 F
            └─┴─ 标记 F = 找到了
└─────┬─────┘
      └─ file_size = 921654 的十进制，反序
```

> 这不是笔误。`x_d0 = bcd_size[3:0]` 是十进制**最低位**，而 `s0` 驱动物理**最左**位。
> 判断的时候只需要认两件事：**右端是 `F`**、**左边 7 位倒过来读是 `0921654`**。
> state_code 同理 —— 屏幕上它出现在**最左端**。

> **为什么不再轮换**：轮换要等 1.5 秒，还要靠"小数点在几位"记住当前是哪个视图，
> 读数容易记错，也没法一眼判断"到底对上没有"。固定显示把最关键的
> `file_size` 一直摆在眼前，判断就一句话——是不是 `F0921654`。
>
> 另外注意：早期版本把 found 标记放在 `d0`（最右）、BCD 数字放在 `d1..d6`，
> 于是 921654 会显示成 `F9216549` —— 末尾那个 `9` 是标记不是数字，
> 很容易读成"末位多了个 9"。现在 `d0..d6` 是纯数字。
>
> `first_cluster` / 每簇扇区数 / 保留扇区数 这些不再上数码管了，
> 要看的话用 ChipProbe 抓，路径见 4.2 节。

**看不到 `9`** 说明位流是旧的或者下载没生效 —— 先比 `bit` 和
`fat32_probe_top.v` 的时间戳，别急着改逻辑。

### 4.2 ILA（ChipProbe）——权威判据

数码管够用，但 ILA 能看到更多、更准。要抓的信号：

| 信号路径 | 说明 |
|---|---|
| `u_fat32/found` | 是否找到 `01.BMP` |
| `u_fat32/file_size[31:0]` | **应为 0x000E11B6** |
| `u_fat32/first_cluster[31:0]` | 文件起始簇 |
| `u_fat32/state_code[3:0]` | 状态机当前状态 |
| `u_fat32/spc[7:0]` | 每簇扇区数（4KB/簇 = 8） |
| `u_fat32/reserved_sec[15:0]` | 保留扇区数 |
| `u_fat32/part_start[31:0]` | 分区起始 LBA（读 MBR 的结果） |
| `u_fat32/data_start[31:0]` | 数据区起始 LBA |
| `u_fat32/fat_size[31:0]` | 每份 FAT 占多少扇区 |
| `u_fat32/root_cluster[31:0]` | 根目录起始簇（通常 2） |
| `u_fat32/open_done` | 打开流程结束（单拍） |
| `u_fat32/xl_valid` / `xl_lba[31:0]` | 翻译结果（本步不一定用到） |

**触发条件**：`u_fat32/open_done` 上升沿。
一次触发就能看到打开流程结束时的全部结果。

**怎么配**（工程里没有现成的 `.cpc`，走 GUI）：

1. 先跑一次综合
2. 打开 ChipProbe / Debugger 界面，从网表里按上面路径选信号
   （`insert_debugger` / `setup_debugger` 是 TD 流程脚本里的标准步骤，
   你的 `_tdflow.tcl` 第 127/231 行就在调它们）
3. 把 `open_done` 设为触发条件（上升沿）
4. 重新综合 + 布局布线 + 生成 bit（插了调试逻辑必须重跑）
5. 下载，打开波形窗口，插上卡/按复位

> ⚠ **具体菜单位置我不确定**。TD 各版本的 ChipProbe 入口和信号选择界面
> 差别不小，我这里只能给出信号路径和触发条件。如果你更习惯用 GUI，
> 按你平时的方式选这些信号名即可 —— 路径名是确定的。

|---|---|---|
| `sd_init_done` | 上电 ~100ms 后拉高 | 不拉高见第 6 节第 1 条 |
| `found` | **1** | |

## 6. 失败时怎么定位

`state_code` 停在哪里是最直接的线索：

| 停在 | 状态 | 说明 | 查什么 |
|---|---|---|---|
| 1 | `S_IDLE` | 一直没开始 | `sd_init_done` 是否为 1 |
| 2 | `S_MBR_REQ` | 卡在读 MBR | 卡住说明扇区读没响应：量 MISO 上拉、看 `sd_dclk` 有没有波形 |
| 3 | `S_VBR_REQ` | 卡在读引导扇区 | `part_start` 是不是个离谱的值（说明 MBR 分区表解析错了） |
| 4 | `S_DIR_REQ` | 在遍历目录 | 正常会停一下然后跳 6；一直停着说明扇区读超时 |
| 5 | `S_DCHAIN_REQ` | 目录跨簇 | 根目录不该跨簇；出现说明 BPB 的根目录簇或 FAT 起始算错了 |
| 6 | `S_OPEN_END` | ✅ 打开流程正常结束 | 看 `found`，0 就是没匹配上文件名 |
| 7 / 8 | 翻译阶段 | 本步不该到 | 探针不发 `xl_req` |

**`found=0` 专查**（这是最常见的失败）：

1. 文件是不是叫 `01.BMP` —— 用 `cmd` 里 `dir /x` 看**短名**。
   Windows 可能显示 `01.BMP` 但短名是 `01~1.BMP` 之类。
   本模块比的是短名域（8+3 空格补齐），不是长名。
2. 有没有隐藏扩展名 —— `01.BMP.txt` 之类的，短名会是 `01~1.BMP`。
3. 是不是放在根目录（不是子目录里）。
4. 文件大小是不是 921654 —— `found` 只看名字，不看大小，
   所以大小不对**不会**导致 `found=0`，而是会导致 `file_size` 不对。

**`found=1` 但 `file_size` 不对**：

说明匹配到了别的目录项。最可能是**卷标项**（属性 `0x08`）或**子目录项**
（属性 `0x10`）。这两种在本模块里是被排除的，如果真发生了，
把卡上根目录的内容贴出来，我回头看 `dir_isfile` 的判断。

**数码管完全不动 / 8 位全灭**：

先看有没有出现过 `9`（上电头 6 秒）。
- 有 `9` 之后才不动 → 扫描在跑，是数据的问题，看 `d7` 是 `F` 还是 `E`
- **从头到尾没有 `9`、全灭** → `seg_scan` 没在动，查 `por_rst_n` 或
  `seg_sel` 的极性；这跟 SD 卡、FAT32 都没有关系
